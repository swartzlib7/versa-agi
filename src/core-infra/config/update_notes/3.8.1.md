# 3.8.1 — Times are local, in and out

## Maintenance after this update

Before this release, the text given to `--due-date` was stored exactly as typed and compared with UTC. From this release a typed time is read in the host's time zone, and every time you are shown is in that zone.

Nothing below is known to be true on this instance. Make each check once and do what its result calls for.

1. **A rule about converting times.**
   - Check: your system memory, awareness and pins, for a rule about UTC, adding or subtracting hours, or converting a time before scheduling.
   - If you find one: supersede or delete it. From this release it makes tasks fire at the wrong time.
   - If you find none: there is nothing to do.
2. **Due times of open tasks.**
   - Check: `agictl task list --all`. For each task that is not done or cancelled, is the time shown the time that was meant? A due date typed as plain local time before this release now shows earlier than intended by this host's offset from UTC (the offset is in CYCLE PARAMETERS). One typed in UTC shows the intended time.
   - If a time is wrong: `agictl task update <id> --due-date "YYYY-MM-DD HH:MM"`.
   - If you cannot tell what was meant: leave the task and ask whoever requested it.
   - If every time is right: there is nothing to do.
3. **The other agents.** This note went to you only.
   - Check: their open tasks in the same list, and whether any of them holds a rule like the one in item 1.
   - If an agent is affected: correct its tasks, tell it by internal message that times are local in and out with no conversion, or give it a specific task to check its own.
   - If none is affected: there is nothing to do.
4. **Scripts that read a time from `agictl`.**
   - Check: your script tasks and shared tools, for one that reads a time field (`created_at`, `updated_at`, `due_date`) out of `agictl` output.
   - If one reads it from `agictl organization … get / list`: add `--stored` to that call. It then gets the stored UTC value, as before.
   - If one reads it from another command: the value now looks like `2026-11-13 11:30 EST`. Change the script to read that form.
   - If none does: there is nothing to do.

## Tell the Primary User

- Times in agitop, and in everything the agents report, are now in this machine's time zone.
- The result of your checks: whether a conversion rule existed, which tasks you changed, and which agents or scripts you had to correct, if any.
